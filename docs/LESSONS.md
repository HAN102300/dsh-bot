# LESSONS — 从事故蒸馏的工程原则

> 这份文档是 [docs/archive/](./archive/) 里全部事故复盘的蒸馏。
> 原文保留了完整现场；这里只留可复用的原则。
> 每一条都来自真实的故障，不是从别处抄的最佳实践。

## 一、失败必须可见

**1. 一个失败不能放大成全部失败。**
一个 `try/catch` 包住一串工具注册，一个未定义变量（`nowIso`）让 14 个工具静默消失，页面照常渲染。
→ 每个注册块独立 catch + 注册后断言数量（现在有 plugin-load.test.ts）。

**2. 成功必须意味着真的做了事。**
空输出 + 0 token + 0 成本曾被标记为 `success`——看起来跑通了，其实模型一次都没被调用。
→ 空输出 = failed（EMPTY_OUTPUT）；演习有拦截 = partial，不是 success。

**3. `try/catch` + 降级返回值 = 错误隐身。**
降级本身没错，错在降级后没有把「我降级了」暴露到显眼处（`os is not defined` 静默降级到错误 provider）。
→ 降级必须带 `degraded` 标记，且降级结果不覆盖配置默认值。

**4. 0 和「不知道」必须长得不一样。**
`¥0.0000` 同时表示「真免费」和「算不出来」——误导性 UI。
→ 成本三态（exact/free/unknown），展示层禁止裸 `toFixed`（未知时那是 undefined，会直接抛错）。

**5. 静默丢弃比迟到更糟。**
错峰推迟的任务曾只记一个时间戳就丢掉——推迟时刻不匹配 cron，任务永久蒸发，界面还显示「已错峰」。
→ 承诺的执行必须有持久化队列；迟到也执行。

**6. 失败时用户看得见吗？**
这是验收每个功能时多问的一句：算不出成本显示「未知」，模型不存在在配置时就拒绝，没节奏用警告色说「它不会自己跑」。

## 二、承诺与实现之间不能有缝

**7. 承诺的能力必须有真实执行路径。**
用户写下「每过 4 小时」，调度器却从不看目标——目标只是一句愿望。产品承诺的能力在代码里没有路径时，用户会先相信它，然后在最需要的时候失望。
→ 写下的每一句自然语言，不去解析就等于没写。

**8. 执行入口必须唯一。**
预算检查曾只设在两个工具入口，调度器与面板路径绕过——同一个承诺三条路径两种兑现。
→ 预算门收口在 RoutineRunner（所有路径共用的唯一入口）。

**9. 撤销本身必须可撤销。**
回滚曾直接覆盖工作区、事先不打快照——回滚选错，回滚前的状态永久丢失。一个卖「收得回」的产品，自己的回滚收不回。
→ restore 前自动快照；归档引用的快照豁免滚动清理。

**10. 能力不存在就不给开关。**
设置页曾有五组「存了没人读」的死配置——用户配置不存在功能，是被辜负的信任。
→ 删掉；功能落地时再出现。

## 三、文档与注释

**11. 文档不许手抄代码。**
README 18 个工具、API.md 15 个、manifest 21 个、实际 22 个——四个数字四个出处。
→ 清单从代码自动生成（`node dev/gen-tools-doc.mjs`），手抄必过期，过期即错。

**12. 注释不许许诺代码没有的东西。**
快照模块头注释宣称「内容寻址 / 增量」，实现从来是全量复制。
→ 注释描述现状，不描述愿望。

**13. 块注释里不能出现 `*/` 序列。**
`bot_*/routine_*` 写进注释，`*/` 提前闭合了注释块，整个文件语法错误。
→ 注释里的通配符写法要用空格隔开（`bot_ 与 routine_ 前缀`）。

## 四、验证文化

**14. 编译期防线是最便宜的防线。**
`tsc` 曾报 123 个错误、被「过滤着看」——`nowIso`/`os`/`expandHome` 三次同类事故全在这 123 个里面。
→ 阶段 0 修到 0 错，`verify:all` 前置 typecheck。词法检查脚本（check-undefined.mjs）是没修好 tsc 前的绷带。

**15. 任何防线要证明能抓到问题。**
一个永远通过的检查等于没有检查。check-undefined 曾故意删掉 import 验证能抓到。
→ 测试覆盖时间换算却没覆盖 tick+shift 组合路径——三个 P0 全在测试盲区。新防线上线前先证明它能红。

**16. 测试钉死环境，不许依赖运行时刻。**
调度测试曾在高峰时段全挂（错峰把触发挪走了）。
→ 测试里显式关掉错峰 / 用固定日期。

## 五、协作与流程

**19. 测试 fake 的形状 ≠ 宿主真身的形状。**
工具循环单测里 fake 的 `tools.list()` 返回 `{name}` 对象数组，测试全绿；
真机上宿主返回的形状对不上（且原生 tools 选项被适配器静默丢弃），
模型自述「没有可用工具」，Bot 每 4 小时空转烧钱。用户建了又删——
这是「看起来一切正常」的另一种形态：不是静默失败，是**静默没挂载**。
→ 凡是从宿主/外部拿的东西，落盘诊断它的真实形状
  （`diag.hostTools = { count, probeMethod, sample }`）；
  归一化做在消费端，不信任生产端；
  协议选不依赖中间层能力的（文本协议），原生能力只做增强。



**17. 做快照回滚产品的仓库，自己必须有快照。**
1 万行代码曾零版本控制。`git init` 是全项目性价比最高的一个修复。

**18. 每个阶段独立成提交。**
回滚基线比回滚机制更早可用。

## #20 包名即身份：改 package.json name 会打断 client graph 对账（2026-10-25）

- **现象**：npm 发布需要 scoped 包名，把 `package.json` 的 `name` 从 `dsh-bot` 改为
  `@zifeng1023/dsh-bot`。此后宿主每次重启 host 侧完全正常（24 工具注册、0 错误、
  调度器照跑），但 client bundle 在浏览器端**从未执行**——面板整体消失，且
  禁用/启用插件、多次重启、硬刷新均无效。
- **根因**：`dsh-client-modules` 对每个已装插件做 `incremental dsh.client scan`，
  client bundle 的「插件→URL」图谱按包名对账。`link:` 安装的插件改名后，
  旧图谱条目失效、新条目未被增量扫描收录，client 图谱里这个插件就"消失"了。
- **诊断关键**：`~/.dsh/bot/.client-status.json` 只收到 host 侧状态；给 client bundle
  顶部加「文件级哨兵」（factory 之前直接 fetch 上报），重启后零上报 →
  一次性区分「文件没被加载」vs「加载后抛错」。这个二分法省掉了整条盲修路。
- **修复**：本地包名回滚为 `dsh-bot`。npm 侧已发布的 `@zifeng1023/dsh-bot` 保留
  （收录走 GitHub url + repository 字段映射，npm 包名与本地开发名允许不同）。
- **规则**：`link:` 本地开发插件的 package.json `name` 是宿主多处的对账主键
  （client graph / dsh.profile.bundles / loader entry），**发布需求也不能改名——
  要么一开始就用 scoped 名，要么用 `files`+`publishConfig` 双名技巧并自测 client 激活**。

## #21 「点击才渲染」的路径是测试盲区（2026-10-26）

- **现象**：运行详情弹窗点开即白屏——`new Set(arr).filter()`（Set 无 filter）
  抛 TypeError，React 整树崩溃。当时 330 个单测全绿。
- **根因**：所有单测覆盖的是数据与宿主契约；**弹窗是点击后才渲染的 React 路径**，
  没有任何测试触达。写代码时把 filter 挂在了 Set 上（思维里还是数组链式调用），
  语法检查、类型检查、单测三道门全部放行。
- **修复**：Set 构造前先对数组 filter；正则字面量改 RegExp 构造器
  （正则字面量里的转义歧义已两次浪费时间——`\\` 层级在字符串/字面量/宿主
  三层之间数不清）。
- **规则**：新增「点击才渲染」的 UI 块时，必须写一个**渲染级冒烟**——
  用最小 React stub 把组件函数真跑一遍（h() 展开即抓 TypeError），
  进 `verify:all`。单纯「文件能 build」不等于「点开不崩」。

## #22 宿主小版本会改契约：接口要按版本双写（2026-11-06）

- **现象**：DSH 升到 0.2.2-rc.1 后，`ctx.tools.execute(单对象)` 变成 `execute(ToolBatchInput{calls,signal})`，
  返回也从单个 `ToolExecutionResult` 变成 `{results:[{callId,result}]}`。桥接层若只按 0.2.1 写，
  在 0.2.2 上工具步骤会整条失效——而注册、面板、调度看起来都正常。
- **根因**：把宿主 rc 版本当成「补丁级、不会变」。实际上 0.2.2 是同 minor 内的执行器重构
  （native/PTC 拆成独立插件 + 批量执行 + 条件工具），属于契约变更。
- **另一个坑**：`engines.dsh` 写 `>=0.2.1-rc.1 <0.3.0-0` 时，普通 semver 不把 `0.2.2-rc.1` 算进范围；
  宿主自己用 `includePrerelease: true` 判定所以放行了，于是「npm 严格校验会挂、真机又能跑」的假象。
- **规则**：
  1. 宿主 rc/minor 升级 → 先 diff 宿主包的 `.d.ts`，再决定改不改；不要只看版本号。
  2. 对外接口按版本双写（批量优先、单次回退），且回退只认入参校验类错误，业务错误原样抛出。
  3. `engines.dsh` 写 `>=0.2.0-0 <0.3.0-0`，覆盖全部 0.2.x 预发布，同时挡住 0.3。
  4. 发版清单加一步「跨宿主各跑一次工具调用」，只测一版等于没测。

## #23 配置写进存储 ≠ 被消费（2026-11-09）

- **现象**：单 Bot 设置文件里明明写着 `notifyOnlyOnDecision: false`，定时运行成功却**没有任何系统通知**；
  用户在 0:00 与 12:00 两次都守着 DSH，仍一无所获。
- **根因**：通知轮询只读全局 `/settings`，从不查单 Bot 覆盖。存储层早在 `SettingsStore.resolve(botId)`
  里实现了「单 Bot 覆盖全局」，但消费端没有按同一作用域取——配置写进去了，没人读。
- **诊断**：`.client-status.json` 里 `notify poller armed` 说明轮询在跑；运行记录 `trigger=goal` 且成功，
  说明被「仅异常打扰」过滤了。两者一对照，问题从「通知没弹」收敛到「策略读错了作用域」。
- **规则**：
  1. 任何「全局 + 单对象覆盖」的配置，所有读取方必须按同一作用域解析，不能一半读全局。
  2. 写一条用例锁住覆盖关系（本次：settings.test.ts）。
  3. 客户端调用点加断言（本次：`verify:client` 检查 `/settings?botId=`），让「忘了传作用域」在构建期就红。

## #24 文本锚点插入函数，必须验证落点作用域（2026-11-13）

- **现象**：执行周期改成结构化控件后，点「编辑」整个 Bot 面板直接消失，诊断里是
  `render-error: describeCadence is not defined`。
- **根因**：用「timeToCron 之后第一个 `\n  }`」做插入锚点，实际匹配到了 `report()` 的
  `try/catch` 闭合处——三个纯函数被塞进了 `report` 的函数体，模块作用域根本看不到它们。
  语法检查、构建、单测全绿，因为代码本身是合法的，只是作用域错了。
- **规则**：
  1. 用文本锚点插入函数时，锚点要包含足够的上下文（整行 + 前后唯一语句），并且插入后检查
     「目标函数是否在预期作用域」——本次在 `verify:client` 里加了括号配对的作用域断言。
  2. 渲染期函数必须在模块作用域，且定义在 `apply` 之前；这类错误只有真机渲染才会暴露。

## #25 10px 的正文不是「紧凑」，是不可读（2026-11-15）

- **现象**：用户看了侧边栏插件页后说「UI、宽度、文字大小都小气，标题和次级内容区分度不够，
  好像都是一个尺寸」。页面并没有明显 bug，也能用。
- **量化**：整份 client bundle 有 133 处 `fontSize`，只有 7 个取值；**10px×42、11px×54**，
  即 72% 的文字是 10–11px，91% ≤12px。而宿主同款插件（CodeArts 1.4.1）的卡片是
  15/22 标题、13/20 描述、14/22 状态行、12/18 元信息、20/1.4 页面标题。
  我们比宿主整体小 2–3px，且缺 14/15 两档，所以「只有标题和正文两种尺寸」。
- **根因**：每加一个小组件就顺手写一个更小的字号，没有人守「尺度」；也没有对照宿主既有插件。
- **规则**：
  1. 正文 13px、元信息 12px、分组小标签 11px，**任何字号不得 <11px**；
  2. 一个页面至少 4 级（20/15/13/12），标题与正文之间必须有过渡档；
  3. 数值尺度写进常量，构建期用正则扫描 CSS 区间的 `font-size` 下限（0.3.8 已加）。
  4. 做 UI 前先量一份宿主既有插件的真实数值，不要凭感觉「紧凑一点」。

## #26 管理能力放在默认收起的面板里 = 不存在（2026-11-15）

- **现象**：用户说「创建的 Bot 查看以及管理好像缺失」。实际功能全都有——只是路径是
  「对话输入框的 Bot 卡片 → 展开浮层 → 行内详情 → 更多 → 配置与危险操作」四层；
  而用户认知里的插件页（侧边栏 `main`）只有设置和诊断。
- **根因**：把能力放在「离对话最近」的地方，误以为用户会顺着入口探索；但默认收起 + 多层折叠，
  在产品感知上等于没有。真正的判据是「用户会不会在插件页里找到」。
- **规则**：
  1. 核心能力必须出现在主入口首屏；折叠只用于「低频 + 高风险」，不能用于「主要工作」。
  2. 列表与详情分离：主视图给「现在需要你知道的」，完整管理进独立详情页。
  3. 详情页允许长，但必须让用户知道怎么回来（`← 概览`）以及怎么继续看（滚动）。

## #27 双栏「各自滚动」：页面不滚，子容器才滚（2026-11-15）

- **需求**：左列表只有 3 个 Bot 很短，右详情很长；用户要求「左侧吸顶，左右两侧都需要滚动」。
- **做法**：外层 `height:100%; overflow:hidden`，页面本身不产生滚动条；左栏 `display:flex;`
  `flex-direction:column`，列表区 `flex:1; min-height:0; overflow-y:auto`；
  右栏 `overflow-y:auto`，头部 `position:sticky; top:0` + `backdrop-filter`。
- **坑**：只给左栏 `position:sticky` 不够——只要外层页面还在滚，列表会先滚出视口。
  `min-height:0` 也必须有，否则 flex 子项不肯收缩，滚动条不会出现。
- **验证**：用 `v038-detail.html#bottom` 的静态稿把右栏滚到底截图，确认左栏与头部都没动。

## #28 弹窗字段必须自派生，不能假设数据形态一致（2026-11-15）

- **现象**：详情页点开运行记录，弹窗标题是「运行详情 · undefined」、步骤数 0、运行输出「无」。
  同一份弹窗在旧 dock 里显示正常。
- **根因**：弹窗读 `run.botName / run.stepCount / run.outputPreview`。这三个字段只有
  `/runs/list` 这一个入口在返回前构造；详情页用的 `/bot` 接口返回的是**原始 RunRecord**，
  根本没有这三个字段——而 `stepCount` 在任何入口都不存在（真实字段是 `steps` 数组）。
  同一个组件被两个数据源喂，组件假设了其中较"胖"的那个形态。
- **规则**：
  1. 渲染组件前先列出它读的每个字段，再核对**每一个**调用点的数据形态；多入口共用的组件，
     要么在入口统一整形，要么在组件内自派生并给兜底（本次选择后者）。
  2. 「不存在字段的默认值」要用真实字段推导（`steps.length`），不要复制一个听起来合理的名字
     （`stepCount` 就是这么写出来的——它像存在，实际从来没有）。
  3. verify-client 加静态断言：弹窗不得引用 `run.stepCount`，必须从 steps 派生（#15）。

## #29 共用组件的 CSS 变量要跟着组件走，不能留在"原页面"的根类上（2026-11-15）

- **现象**：官方设置页的 Bot 分区复用了主页面组件后，开关只剩一个白点、卡片没有底色、
  危险按钮只剩文字——用户截图：「样式好像丢了？开关都看不见了」。
- **根因**：组件的全部配色都读 `--c-*` 变量，而这组变量声明在主页面根类 `.dsh-bot-c` 上。
  组件被搬进官方设置页后，渲染树里没有这个祖先，所有 `var(--c-…)` 同时落空——
  文字有内联颜色所以还能看，凡是靠变量的面/轨/线全部消失。
- **修复**：把变量声明抽成 `.dsh-bot-c, .dsh-bot-c-vars { … }`，设置页容器挂 `-c-vars`；
  开关轨道/开启色再补一层宿主令牌兜底（`bg-layer-3` / `brand-primary` 的 var 兜底链）。
- **规则**：
  1. 抽组件时先问"它依赖哪些祖先提供的 CSS 变量/类"，把这些依赖**随组件一起搬**；
  2. var() 兜底链不要省——`var(--c-x, var(--dsw-alias-y, fallback))`，两层兜底只多两行；
  3. "复用组件"的验收必须包含**脱离原页面单独渲染**的截图（本次用 harness 的
     `#settings-section` 路由离屏渲染验证），不能只看主页面对不对。

## #30 抽组件时，内联在组件里的「就地派生变量」必须跟着一起搬（2026-11-20）

- **现象**：v0.3.9 刀 1 真机点开模型快切、选中一个模型后，**整条快捷条凭空消失**，
  界面只剩输入框。浏览器控制台里 React 整棵树被卸载，没有任何提示。
- **根因**：把模型菜单从 `DockBar` 抽成独立组件 `ModelMenu` 时，`modelsFor`
  （由 `pickProvider` 派生的模型子列表）留在了 `DockBar` 作用域里，而
  `ModelMenu` 的「模型列表」分支仍引用它 → `ReferenceError: modelsFor is not defined`
  → 渲染抛错 → 无 ErrorBoundary → React 18 卸载整棵子树 → 快捷条消失。
- **为什么测试没抓到**：渲染用例只覆盖了「provider 列表」分支（`pickProvider = null`），
  崩溃发生在**另一个三元分支**里。一个组件的每个条件分支都是独立的渲染路径。
- **修复**：`modelsFor` 移进 `ModelMenu` 作用域；verify-client 增加「模型列表分支」用例
  （`pickProvider = 'deepseek-account'`）；harness 加 ErrorBoundary，让渲染错误带栈落 DOM。
- **规则**：
  1. 抽组件 = 连同**它读到的每一个本地派生值**一起搬，不是只搬 JSX；
  2. 三元/条件渲染的**每个分支**都要有独立渲染断言，只测 happy path 等于没测；
  3. 调试 UI 崩溃先上 **ErrorBoundary + 把栈写进 DOM**，靠截图猜是浪费时间；
  4. 组件内不要留"临时调试钩子"到生产——本次加过 `window.__DOCK_DEBUG__`，验证完即删。

## #31 空状态元素不能只靠 CSS 藏，要直接不渲染（2026-11-20）

- **现象**：快捷条下方一直挂着一颗灰色小方块，用户问「这方块是干嘛的，UI 位置错乱？」。
- **根因**：toast 容器写成 `portal(h('div', { className: '-db-toast' }, toast))`，
  `toast` 为空串时**元素仍然渲染**（只是没有文字）。`position: fixed` + 背景 + 圆角
  → 屏幕上就是一颗孤立的灰块。
- **修复**：`toast ? portal(...) : null`，并且真正未使用时不创建 DOM。
- **规则**：空态要么不渲染（首选），要么 `hidden`/`display:none`；不要留下"空壳元素"——
  它有尺寸、有背景，用户只能看到一颗不明方块。

## #32 贴在输入框上方的条，宽度必须抄输入框卡片的约束（2026-11-20）

- **现象**：新版快捷条在宽窗口下**拉满整行**，与下方输入框格格不入（用户原话）。
- **根因**：只套了 `width: calc(100% - clearance*2 - inset*4)`。宿主里这两个变量为 0 时，
  这条式子等于 `100%`；旧面板之所以不宽，是因为它**外层还有一层**
  `max-width: calc(var(--dsh-composer-card-max-width, 748px) - inset*4)`，
  抽新组件时只搬了外层宽度，没搬内层上限。
- **修复**：`.${NS}-dockbar` 自身加 `max-width: calc(var(--dsh-composer-card-max-width, 748px) - var(--dsh-composer-dock-inset, 0px) * 4)`
  并 `margin-inline: auto`；兜底 748px 就是官方输入框卡片宽度。
- **规则**：宿主变量的"兜底值"就是**没有宿主变量时该长什么样**。凡是写 `var(--x, 0px)`
  的地方，先问一句"宿主没注入时它是不是就等于没约束"。

## #33 图标用 SVG，不要在 UI 里裸写字符（2026-11-20）

- **现象**：收起按钮渲染成一个 `⌃`、模型下拉是 `▾`，用户直接说「不觉得丑吗」。
- **根因**：字符字形由**宿主字体**决定，字号/字重/基线都不受控，在不同系统上与周围
  11–12px 文字永远对不齐；而且 `⌃`（U+2303）在很多字体里是数学符号，不是箭头。
- **修复**：`ChevDown` / `ChevUp` 两个 12×12 的 SVG 雪佛龙组件，`stroke-width 1.4`、
  `stroke-linecap: round`，尺寸参数化（`size`），颜色 `currentColor` 跟随文字。
- **规则**：UI 里只允许两类图标——(1) 自带 SVG；(2) 宿主令牌里的图标组件。
  emoji、`▾ ⌃ ← →` 这类字符一律禁止（中文字体下宽度/基线必然错位）。

## #34 一行布局不稳，先分「可裁剪区 / 不可裁剪区」（2026-11-20）

- **现象**：快捷条内容一多（Bot 名长、模型名长），右侧「收起」按钮被挤出可视区；
  文字还会溢出自己的盒子，压在邻居身上（`¥5.00deepseek-account`）。
- **根因**：
  1. 一整行 flex 没有分区——所有子项"公平"参与压缩，结果该保的按钮被压缩、该截断的文字溢出；
  2. `overflow:hidden` 只加在容器上，flex 子项里的文本节点没有块级化，`text-overflow:ellipsis` 不生效；
  3. 弹层是行的子节点，容器一加 `overflow:hidden`，弹层也被一起裁掉。
- **修复**：行内分两段——`.dockbar-main`（`flex:1 1 auto; min-width:0; overflow:hidden`，承担压缩）
  + `.dockbar-actions`（`flex:0 0 auto`，永不压缩）；文本子元素 `display:block` 才吃 ellipsis；
  弹层提到行的**兄弟层**，靠父容器 `position:relative` 定位。
- **规则**：
  1. 任何"一行里既有弹性内容又有固定操作"的布局，**先分区再排**，不要指望 flex 自动公平；
  2. `text-overflow: ellipsis` 的三个前提：块级容器 + `overflow:hidden` + 有确定宽度约束；
  3. 需要溢出显示的子元素（菜单/气泡/角标），**不能放在有 overflow:hidden 的盒子里**。

## #35 一个控件只做一件事；多个控件做同一件事一定会被用户骂（2026-11-20）

- **现象**：收起态里点 Bot 名、点状态点、点模型名，**全都跳到管理中心**。用户原话：
  「你在干什么？」。
- **根因**：为了省事，把三个入口的 `onClick` 都写成 `openConsoleSafe`——反正"能到管理中心就行"。
- **修复**：按控件的语义分别接线：Bot 名 → Bot 菜单、状态点 → 运行记录（管理中心）、
  模型 → 模型菜单、箭头 → 展开/收起。收起态与展开态共用同一套弹层组件，行为一致。
- **规则**：
  1. 控件的点击行为必须能从**外观**预测——名字就是"切换"，模型就是"换模型"；
  2. 状态类信息（圆点/徽标）点击去"看详情"是合理兜底，但**不能成为所有控件的统一行为**；
  3. 两种形态（收起/展开）里同名控件必须同义，否则用户会觉得"到处都是同一个跳转"。

## #36 UI 的「二次确认」必须落到请求体，否则服务端会当作未确认（2026-11-20）

- **现象**：快捷条点「执行 → 真跑一次」，弹出 toast「启动失败：真实执行必须显式传 confirm: true」，
  运行根本没启动。演习同样会被挡。
- **根因**：`POST /run` 有一道安全校验 `body.confirm === true`（任何执行都必须显式确认）；
  快捷条在 UI 上已经让用户点过一次确认浮层，但**请求体里没带 confirm**——
  前端以为"我确认过了"，服务端只认 payload。UI 的确认与协议的确认是两件事。
- **修复**：`doRun` 无论演习还是真跑都带 `confirm: true`（用户点下浮层按钮那一刻即为显式确认）；
  verify-client 增加断言钉住请求体形状。
- **规则**：
  1. 前端每加一层"确认步骤"，先回头看服务端的校验要求——**两边的确认语义要成对**；
  2. 有 `confirm`/`dryRun` 这类安全参数的端点，客户端断言要匹配**完整请求体**，不是只匹配 URL；
  3. 同一入口的不同模式（演习/真跑）要分别验证请求体，别只测一条路径。

## #37 状态文案要区分「演习中」与「真跑中」（2026-11-20）

- **现象**：点「真跑一次」后，状态条仍显示「演习中」，用户会以为真跑没生效。
- **根因**：`dockStatOf(bot, running)` 只判断"是否在跑"，没记录"跑的是哪种"。
- **修复**：新增 `runningDry` 状态，在发起时记录；状态条与按钮文案分别为「演习中 / 真跑中」。
  注意：新 `useState` 必须放在**既有 hooks 之后**、且使用它的计算要移到**所有 hooks 之后**
  （否则 `Cannot access 'x' before initialization` —— 本次就在 verify 阶段被抓到）。

## #38 「失败」有两种到达方式：抛异常，或 finish 块里带 reason.kind=error（2026-11-24）

- **现象**：社区 issue #1 —— 所有执行在 4–18ms 内失败，报「模型返回了空内容」，
  `usage` 全 0、无网络往返。看起来像网关/密钥问题，实际是宿主在校验阶段就拒绝了。
- **根因**（两个独立缺陷叠加）：
  1. 插件无条件下发 `reasoningEffort`，而宿主对「模型条目未声明 reasoning」直接抛
     `UNSUPPORTED_REASONING_EFFORT`；
  2. 宿主的失败传递是 `{ type:"finish", reason:{ kind:"error", failure } }`，**不是** `type:"error"`。
     我们的 `case "finish"` 只存 `stopReason`，于是真实失败落进「空输出」分支被吞掉。
- **修复**：条件下发 effort（缺失就不传）+ `finish` 分支识别 `reason.kind` + 抛错用
  `failure.code/message` + 命中 `UNSUPPORTED_REASONING_EFFORT` 时自动去掉 effort 重试一次。
- **规则**：
  1. 对接流式协议时，**先把「失败」的所有到达路径列全**（异常抛出 / error 块 / finish+kind），
     再写 switch；只处理自己想到的那一种，真实原因就会被吞成模糊文案；
  2. 报错必须带上游的 `code` —— 「空内容」这种概括性文案会把人引向完全错误的方向；
  3. 能用「自动降级 + 说明」解决的兼容问题，不要只写文档让用户手改配置；
  4. 用户报告的「几毫秒失败、usage 全 0、无网络」是**前置校验失败**的指纹，
     不是网络/鉴权问题——排查时先看请求有没有真的发出去。

## #39 卡片高度必须由容器兜底，不能由内容决定（2026-11-27）

- **现象**：记忆卡 21 条把卡片撑到约 1100px，把下面的配置/快照卡挤到屏幕外；
  每多一条记忆就再高一点。用户反馈「随着记忆越来越多，卡片高度也随之增高」。
- **根因**：列表直接 `rows.map(...)` 平铺在卡片里，卡片没有 `max-height`。
  这在数据少时完全看不出问题，属于典型的「随数据增长才暴露」的布局缺陷。
- **修复**：内层滚动容器 `max-height: 258px; overflow-y: auto` + 底部渐隐；
  底栏给出「共 N 条 · 可滚动查看」，让用户知道还有内容。
- **规则**：
  1. 任何「条目数会随时间增长」的列表，**设计时就要定高度上限**——
     不要等数据变多再改，那时用户已经把页面长度当成常态了；
  2. 限高必须配「还有更多」的视觉提示（渐隐 / 计数 / 展开入口），否则用户不知道要滚；
  3. 渐隐要在滚到底时消失，不然永远有个"没看完"的错觉。
